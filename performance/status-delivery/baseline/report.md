# V2 상태 조회 폴링 기준값 측정 결과

## 측정 목적과 결론

진행률을 제거한 여행·스토리 상태 조회를 대상으로 웹소켓 전환 전의 기준값을 측정했다. API 3종과 동시 사용자 100·500·1,000명을 조합한 9개 조건을 각각 1회 실행했다.

측정 구간의 상태 조회 요청은 총 **249,304회**였다. 모든 조건에서 상태 조회와 고정 지도 조회의 요청 오류율은 0이었고, 전원이 중간 상태 변경과 완료를 확인했다. 완료 상태 인지 p95는 약 **1.7~2.0초**였다.

웹소켓 적용 후에도 같은 상태·시간표·사용자 수를 사용해 전달 지연과 전체 자원 비용을 비교한다.

## 1. 실행 조건

- 코드 기준은 `3ef3260`이다. 여행·스토리 응답에서 `progress`를 제거한 코드다.
- 로컬 Docker에 BE 2개를 실행했다. 각각 1vCPU·2GiB이며 JVM 힙은 256~512MiB, G1 GC다.
- MySQL은 1vCPU·1GiB, Redis는 0.5vCPU·256MiB로 제한했다. AI 응답 대역은 1vCPU·256MiB다.
- Docker 전체 가용 자원은 CPU 10개·약 7.75GiB다. k6는 호스트에서 실행했다. ALB·TLS·브라우저 화면 렌더링은 포함하지 않았다.
- 각 조건은 준비 30초와 측정 120초다. 처음 계획한 3회 반복은 사용자 요청으로 1회로 조정했다.
- 각 사용자는 자신의 인증 정보와 서로 다른 작업을 사용했다. 두 BE로 사용자를 나누어 요청했다.
- 실제 JWT 서명 검증, Redis 로그인 세션 검사, DB 사용자 확인과 기존 Controller·Service·Repository를 사용했다. OAuth 로그인 자체의 부하는 제외했다.
- k6는 요청 응답 후 2초 기다린다. 따라서 요청 처리 시간이 늘면 전체 반복 주기도 늘어난다. 시작 시점은 2초 구간에 분산하고 HTTP 연결을 재사용했다.
- 측정 시작 30초 후 중간 상태를 변경하고, 105초 후 완료시켰다. 완료를 확인한 사용자는 조회를 중단했다. 마지막 약 15초의 조회 중단 구간도 120초 평균에 포함된다.
- 별도 k6 프로세스로 사진이 없는 테스트 사용자의 `GET /trips/map`을 초당 5회 요청했다.

고정 사용자 수와 반복 요청의 관계는 [k6 constant-vus 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-vus/)를 기준으로 해석했다.

## 2. 실제 실행한 시나리오

### 스토리 생성 상태 조회

`GET /api/story-generation/{generationId}`를 반복 호출했다. DB 상태를 QUEUED → PROCESSING → COMPLETED로 전환하고 각 사용자가 새 상태를 처음 받은 시각을 기록했다. 스토리의 BE→AI 스케줄러는 끄고 DB 상태를 통제했다.

### 여행 생성·수정 상태 조회

`GET /api/trips/{tripId}/processing-status`를 반복 호출했다. PROCESSING 동안 AI 응답 대역의 currentStep을 EMBEDDING → CLUSTERING으로 바꾸고, 마지막에 DB 작업을 COMPLETED로 전환했다.

여행 생성·수정의 상태 조회 중 AI HTTP 호출은 실제 코드 그대로 실행했다. AI 계산 대신 형식이 같은 응답 대역을 사용했다. 완료 시 사진·장소 개수는 실험 DB의 실제 집계이며 테스트 자료에 사진이 없어 0이다.

### 측정한 범위

이번 실험은 **이미 주어진 작업 상태를 조회하고 클라이언트가 확인하는 경로**를 측정했다. 사진 업로드·변환·AI 계산·Kafka 결과 저장 전체를 실행하지 않았다. 새로운 웹소켓 엔드포인트나 destination도 결정하지 않았다.

## 3. API 응답과 상태 전달 지연

API 응답 p95는 HTTP 요청이 끝나는 시간이다. 상태 인지 p95는 상태 변경 후 k6가 새 값을 처음 받은 시간이다. p95는 관측값의 약 95%가 그 시간 이내라는 뜻이다. 화면 렌더링 시간은 포함하지 않는다.

## 4. Prometheus·컨테이너 자원 결과

Prometheus는 5초 간격으로 HTTP·CPU·힙·DB 커넥션과 Redis exporter 지표를 수집했다. 각 측정 구간의 시계열 응답을 `runs/<조건>/prometheus.json`에 보존했다. Grafana 화면 캡처를 수치 근거로 사용하지 않았으며, 표는 수집한 원자료에서 계산했다.

| 경로 | 사용자 | BE 합산 평균 CPU(코어) | BE별 평균 힙(MiB) | Redis 명령/초 | MySQL SELECT 증가 | AI 대역 호출 증가 |
|---|---:|---:|---:|---:|---:|---:|
| 스토리 생성 | 100 | 0.223 | 159.9 | 64.8 | 15,498 | 0 |
| 스토리 생성 | 500 | 0.413 | 158.6 | 256.9 | 70,176 | 0 |
| 스토리 생성 | 1,000 | 0.594 | 158.1 | 501.5 | 138,640 | 0 |
| 여행 생성 | 100 | 0.255 | 156.2 | 65.2 | 29,303 | 6,729 |
| 여행 생성 | 500 | 0.572 | 151.5 | 259.3 | 139,337 | 33,635 |
| 여행 생성 | 1,000 | 0.707 | 165.6 | 473.4 | 259,579 | 62,952 |
| 여행 수정 | 100 | 0.240 | 148.6 | 65.1 | 22,581 | 6,722 |
| 여행 수정 | 500 | 0.517 | 162.6 | 260.6 | 105,520 | 33,581 |
| 여행 수정 | 1,000 | 0.702 | 158.6 | 468.0 | 196,568 | 62,928 |

두 JVM은 각각 CPU 1개를 인식한다. BE CPU는 `process_cpu_usage`의 측정 구간 평균을 합산했다. 1.0코어는 CPU 한 개를 계속 사용한 양이고, 두 BE의 할당 합계는 2코어다. 힙은 두 BE와 측정 시점의 평균이다.

MySQL SELECT와 AI 호출 증가량은 준비·완료 확인을 포함한 조건 전체 실행 구간이다. SELECT에는 인증·지도 조회·백그라운드 작업 등도 포함된다. Redis 명령/초·CPU·힙은 측정 120초의 평균이다. 서로 다른 구간의 지표를 API당 정확한 호출 수로 나누지 않는다.

### 1,000명 조건의 Docker 자원 교차 확인

| 경로 | BE 합산 CPU(코어) | BE1 / BE2 평균 메모리(MiB) | MySQL CPU(코어) | Redis CPU(코어) | AI 대역 CPU(코어) |
|---|---:|---:|---:|---:|---:|
| 스토리 생성 | 0.616 | 649.8 / 669.2 | 0.327 | 0.019 | 0.001 |
| 여행 생성 | 0.726 | 653.0 / 673.3 | 0.227 | 0.014 | 0.055 |
| 여행 수정 | 0.725 | 658.0 / 675.1 | 0.213 | 0.015 | 0.057 |

Docker CPU는 100%를 1코어로 환산했다. 메모리는 Docker stats의 컨테이너 사용량이며 JVM 힙과 구분한다. 자세한 평균·최대값은 `analysis.json`에 있다.

## 5. 관측한 내용과 후속 비교 기준

- 스토리 1,000명은 API p95 약 20ms였지만 완료 인지 p95는 약 1.9초였다. API 처리 시간과 다음 폴링까지의 대기는 별도 비용이다.
- 여행 생성·수정 1,000명에서는 API p95가 각각 약 209ms·258ms였다. 동시에 보낸 빈 지도 조회의 p95도 약 175ms·233ms로 증가했다.
- 이때 BE 평균 CPU는 두 개 합계 약 0.7코어였다. 평균 CPU만으로 지연 원인을 단정하지 않고, 웹소켓 전환 후 요청 감소와 지도 조회 지연이 함께 달라지는지 비교한다.
- 여행 생성·수정의 반복 상태 조회는 AI 상태 HTTP 호출로 이어졌다. 상태 수집을 요청별 호출에서 서버 측 수집으로 바꾸면 그 변경도 함께 기록하고, 프로토콜 하나만의 효과로 설명하지 않는다.
- 상태가 몇 번만 바뀌어도 폴링 요청과 인증·조회는 계속 발생했다. 전환 후에는 반복 조회 수, 상태 인지 지연, BE·웹소켓·Redis의 자원 비용을 함께 비교한다.

각 조건 1회 실행의 로컬 기준값이다. 전환 후 차이가 작거나 편차가 의심되는 조건은 추가 반복한다. 운영 최대 수용량이나 사진 처리 속도 산정에는 사용하지 않는다.

후속 실험은 같은 자료 수·상태 시간표·BE 자원을 유지한다. 웹소켓 연결 유지 신호, 30초 인증 재검증, 최초·재연결 상태 조회도 비용에 포함한다. AI 상태 수집 방식과 주기를 바꾸면 변경점을 별도로 기록한다.

## 6. 계측 점검과 제외 자료

사전 실험에서 다음 문제를 발견하고 수정했다.

- 사용자 수에 맞지 않는 요청 시작 시점 분산.
- 상태 조회와 지도 조회를 한 k6 프로세스에서 실행할 때의 사용자 번호 충돌.
- Docker 공유 파일 갱신 중 AI 응답 대역이 파일을 찾지 못한 오류.

해당 자료는 `pilot-runs`, `excluded-pre-fix`, `preflight-final` 등에 별도로 보존하고 본 통계에서 제외했다. 최종 AI 대역은 메모리 상태를 사용하며 상태 조회와 지도 조회는 서로 다른 k6 프로세스로 실행한다.

DB 상태 전환 전후의 DB 시각과 AI 대역의 상태 전환 시각을 기록했다. 매 조건 시작 시 호스트와 Docker의 시각 차이를 5회 왕복 측정 중 최소 RTT 표본으로 보정했다. 밀리초 반올림 경계의 관측도 실제 수신한 상태값으로 식별해 포함했다. 변경 시각 범위·시각 보정값·사용자별 수신 시각을 원자료에 남겼다.

## 7. 원자료와 재현

- `environment.json` — 커밋, JAR 해시, 자원 제한, 실험 범위.
- `summary.csv`, `analysis.json` — 조건별 집계.
- `runs/<조건>/k6-summary.json` — 상태 조회의 k6 원본 요약.
- `runs/<조건>/probe-summary.json` — 고정 지도 조회의 k6 원본 요약.
- `runs/<조건>/events.jsonl` — 사용자별 상태 수신 시각.
- `runs/<조건>/markers.json`, `metadata.json` — 상태 전환 시각과 실행 구간.
- `runs/<조건>/prometheus.json` — Prometheus 시계열 원자료.
- `docker-stats.jsonl` — 컨테이너 자원 원자료.
- `sources/` — 최종 실험 스크립트와 compose 설정.

실제 계정·브라우저 쿠키·운영 데이터는 사용하지 않았다. 합성 계정으로 격리된 로컬 DB·Redis에서 실행했다.
